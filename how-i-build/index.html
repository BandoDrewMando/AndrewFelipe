How I build

I build my personal apps with Claude Code, Anthropic’s coding agent. This page is the whole arrangement: who does what, the rules every app follows, and what stands between the agent and my PC.

Who does what

Me

  • Decide what gets built, and why
  • Write the requirements in plain words
  • Set the rules every app has to follow
  • Use the apps and report what is wrong
  • Approve what Claude proposes on its own, on my phone, with a passkey

Claude Code

  • Starts from the repo and its notes, never from a stale copy
  • Writes the code and the tests
  • Runs the tests, and looks at the page in a real browser
  • Writes down what it learned, in the repo, for the next session
  • Proposes features of its own. It never ships one without my yes

The path of a change

  1. It starts with a sentenceUsually mine, often from my phone: what I want, or what looked wrong. Sometimes Claude’s: a bug the nightly checkup found, or a feature idea from a night shift.
  2. Claude builds from the repoIt pulls the latest first. Several sessions work on the same apps and cannot talk to each other, so the repo is how they stay in step.
  3. Tests, then a second lookThe suite runs. Riskier changes get a separate review pass that reads the change cold. Several of the problems described on these pages were found that way.
  4. The gateWhat I asked for, and bug fixes, go ahead once the tests pass. A feature Claude came up with on its own stops here, in an inbox, with what it is, why it exists, what it changes and a picture.
  5. I say yes on my phoneFor those proposals, Face ID signs a hash of exactly what I was shown. If the proposal changes after I open it, the yes is refused. Try the gate.
  6. Deployed, and written downExactly the pushed commit goes to the PC, and a line goes in that app’s deploy log.

House rules

These are standing rules. Every session reads them before it writes anything.

  • All work goes through the repo. Tested, approved fixes are always committed and pushed, and what is deployed is exactly what was pushed.
  • Idle means idle. An app uses almost nothing when nobody is using it, and gets off the graphics card the moment a game starts.
  • Secrets stay in Windows Credential Manager. Never in a file, a log or a commit.
  • Nothing on the PC says yes for me. A program there can forge any header. It cannot forge my face.
  • Windows security settings are mine. The firewall and sign-in are never changed for me. I get asked.
  • Tests never touch the real thing. A simulated home, a test island, a pretend cloud. Never my own data, my real devices or a live API key.

The notes are part of the code

Each repo carries a notes file that every session reads first and updates last. It records what was decided, when, why, and what was measured, in enough detail that a fresh session with no memory can pick the work up.

One entry, from the home hub’s camera notes, word for word:

Never give a decoder an empty packet: to FFmpeg that means “the stream ended”, and the decoder never gives a picture again (that stopped the front door’s live view, snapshots and person spotting 17 s after a start).

Most of the decisions and bug stories on the project pages come straight from those notes.

Work that runs without me

The daily checkup

Every night a scheduled run goes over all the apps, fixes the bugs it finds and ships the fixes. Its instructions live in the repo, so changing what it does is a commit I can read, and the run is not allowed to edit them itself.

Night shifts, in a box

A longer session can build feature proposals overnight. It runs in a sandbox, because it works alone on a machine full of my things:

  • Its own Linux install under WSL, made from an image whose checksum is verified.
  • An unprivileged user with no password and no sudo.
  • A network of its own with no route out. One allowlist proxy is the only exit, and it opens a short list of sites by name and nothing near home.
  • A system-call filter that also closes the side door WSL keeps open to Windows.
  • A read-only token for the code host, held by root. What the worker builds reaches the repo only after my yes.
  • A spending cap per minute and at most three proposals a night.
  • A second locked-down user that judges what was produced. Every wall is checked before every run, and if one is down, nothing starts.

    Limits, plainly

    • Claude writes the code. My part is the requirements, the rules, using the apps and the yes.
    • The passkey guards what Claude proposes on its own. Fixes, and changes I asked for, go in on the strength of the tests.
    • Shipping an approved proposal is not automatic yet. The trusted deployer is the next piece.
    • All of it is built for one person on one PC.
